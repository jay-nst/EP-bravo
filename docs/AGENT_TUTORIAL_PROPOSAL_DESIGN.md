## Problem Statement

운영 중인 agent.ep.naraspace.com(EarthPaper Agent)에서 신규 사용자가 "어떻게 써야 할지 모르겠다"며 이탈한다. 직접 증언과 Microsoft Clarity 이탈 데이터가 이를 뒷받침한다. 해법으로 게임 튜토리얼식 온보딩(타겟 요소 하이라이트 + 나머지 음영 + 단계별 설명 말풍선, 순서대로 클릭 유도)을 제품에 넣자는 것이 제안의 골자다.

이 설계문서의 산출물은 **실제 제품 내 튜토리얼이 아니라, 그 제안을 통과시키기 위한 기획 시연 페이지**다. 실제 화면 캡쳐 위에 튜토리얼 오버레이가 진짜처럼 동작하는 클릭형 데모를 만들어, 내부 승인자가 직접 클릭하며 체험하게 한다. ep.naraspace.com에 추가 제안하는 별도 페이지 형태.

## Demand Evidence

- **직접 증언**: 사용자들이 어떻게 써야 할지 모르겠다고 직접 말함 (사용자 원문 기준).
- **Clarity 데이터**: 이탈률 등 직접적인 행동 데이터 신호가 존재. 증언과 데이터가 같은 방향을 가리킴.
- **막힘 지점 3개 확인** (세션에서 확정):
  1. **첫 화면 cold-start** — 빈 입력창에서 무엇을 입력해야 할지 모름 (LLM 제품 전형 패턴)
  2. **기능 발견 실패** — 핵심 기능의 존재 자체를 모르고 지나침
  3. **가입/진입 장벽** — 본론 진입 전 이탈

## Status Quo

- 현재 Agent에는 단계별 온보딩 가이드가 없다. 신규 사용자는 빈 화면에서 스스로 파악해야 하며, 실패하면 그대로 이탈한다.
- 외부 벤치마크(2026): 인터랙티브 온보딩이 있는 제품은 활성화율 ~50% 높음. 투어 완주율은 스텝 수가 지배 — **1-2스텝 73%, 3-5스텝 38%, 6-8스텝 25%, 9스텝+ 8%**. 가장 흔한 실패는 "다음-다음-다음" 정적 슬라이드쇼와 기능 전부를 한 투어에 욱여넣기(12스텝 = 완주 16%). UI 변경 시 투어가 깨지면 투어가 없는 것보다 신뢰를 더 해침.
- 라이브러리 지형: driver.js(MIT, ~5KB) / Intro.js·Shepherd.js(**AGPL — 상용 서비스 부적합**) / React Joyride(React 전용, MIT, 최다 사용).

## Target User & Narrowest Wedge

- **1차 고객 (이 페이지의 고객)**: 내부 승인자. 이 페이지가 팔아야 하는 것은 튜토리얼 기능이 아니라 "이 기획을 승인하라"는 결정이다.
- **2차 고객 (튜토리얼의 최종 사용자)**: agent.ep.naraspace.com에 처음 진입한 비전문가 사용자 — 기존 플랫폼 설계문서의 "OO회사 김OO 부장" 페르소나와 동일 선상.
- **Narrowest Wedge**: 실제 화면 캡쳐 위에서 하이라이트+음영+말풍선이 동작하는 클릭형 데모 1개 플로우. 승인자가 "상상해보세요"가 아니라 "직접 써보세요"를 경험하게 하는 최소 단위.

## Constraints

- 화면은 실제 Agent 화면 **캡쳐 이미지**로 대체 (실서비스 연동 없음 — 기획 시연이므로 오히려 정답: UI 변경 리스크·제작 비용 제로, 플로우 통제 가능)
- 스텝 수는 **5개 이하 목표** — 초과할 수 있으나 완주율 데이터를 근거로 최소화 노력
- 기존 EarthPaper 디자인 시스템(DESIGN.md, Pretendard Variable) 준수
- 실구현 시 라이선스 제약: AGPL 라이브러리(Intro.js, Shepherd.js) 배제 → driver.js(MIT) 계열 전제

## Premises

1. **이 페이지의 고객은 내부 승인자다.** 캡쳐 기반 클릭형 데모가 정답이고, 실제 제품 내 튜토리얼 구현은 승인 후 별도 작업. — 합의
2. **튜토리얼 플로우는 5스텝 이하를 목표로 하되, 초과 가능.** 완주율 데이터(3-5스텝 38%, 9+스텝 8%)가 근거. cold-start와 기능 발견에 집중. — 합의 (사용자 수정 반영: 소프트 상한)
3. **튜토리얼은 비로그인 상태에서 진행하고, 마지막에 "진짜 쓰려면 회원가입/로그인" 모달로 전환을 유도한다.** 이로써 튜토리얼이 단순 사용성 개선이 아니라 **비로그인 체험 → 가입 전환 퍼널**이 된다. 막힘 지점 ③(가입/진입 장벽)까지 하나의 장치로 커버. — 합의 (사용자 수정 반영)
4. **실구현 핸드오프 조건을 데모 스펙에 포함한다.** 스텝별 타겟 요소/카피/순서를 구조화된 설정 파일로 분리해, 승인 시 개발팀이 driver.js 계열로 그대로 구현 가능하게. — 합의

## Approaches Considered

### Approach A: 단일 자립 HTML 데모 (minimal viable)
캡쳐 + driver.js(CDN)를 파일 하나에 담은 self-contained HTML. Effort S / Risk Low.
- Pros: 가장 빠름, repo 오염 제로, 파일 공유 가능
- Cons: 디자인 시스템 단절로 "사이드 문서" 느낌, URL 회람 불가

### Approach B: earthpaper Next.js 라우트 + driver.js + 구조화 스텝 스펙 (ideal) — 채택
earthpaper 프로젝트에 제안용 라우트(`/proposals/agent-tutorial`) 추가. 캡쳐 위 투명 핫스팟 div를 driver.js가 타겟팅, 스텝은 설정 파일(`steps.ts`)로 분리. 내부 배포 서버로 URL 회람. Effort M / Risk Low — 단, 스텝 간 캡쳐 전환(훅 기반)이 유일한 비자명 구현 지점(구현 스펙 참조).
- Pros: 데모 = 동작하는 프로토타입 (승인→구현 거리 최소), DESIGN.md 일관성으로 실서비스감, URL 공유
- Cons: A보다 범위 넓음, 반려 시 repo 잔재
- Reuses: earthpaper Next.js 인프라, DESIGN.md, 내부 배포 서버(PM2), /gyeonggi 페이지 작업 패턴

### Approach C: 인터랙티브 스토리형 제안 페이지 (creative)
B 앞뒤로 문제 데이터(Clarity)와 기대효과 섹션 + presenter 토글. Effort M-L / Risk Med.
- Pros: "문제→해법→효과" 자기완결 설득 구조
- Cons: D4에서 클릭형 데모 단독을 선택했으므로 과투자 위험

## Recommended Approach

**Approach B.** 목표가 "제안 통과"인데, B는 데모가 곧 동작하는 프로토타입이라 승인자의 "실제로 되긴 하나?"를 원천 차단하고, 승인 순간 개발 핸드오프가 이미 끝나 있다. 단, C의 핵심 요소 중 **Clarity 근거 한 줄**(도입부)만 가볍게 차용한다 — 페이지 첫 화면에 "왜 이게 필요한가" 수치 1-2개 노출 (수집은 3개, 노출은 1-2개 — 나머지는 실구현 효과 측정 베이스라인용).

**페이지 구성**: ① 도입부(Clarity 수치 1-2개 + 제안 한 줄) → ② 클릭형 튜토리얼 데모(본체) → ③ 아웃트로(기대효과·측정 지표 — 아래 Success Criteria 2차 항목). 라우트 경로: `/proposals/agent-tutorial`.

### 튜토리얼 플로우 초안 (5스텝 목표, 캡쳐 기반)

| 스텝 | 막힘 지점 | 내용 (초안) |
|------|-----------|-------------|
| 1 | cold-start | 첫 화면: 입력창 하이라이트 + 예시 프롬프트 2-3개 제시 ("이런 걸 물어볼 수 있어요") |
| 2 | cold-start | 예시 프롬프트 클릭 → 결과 화면 캡쳐로 전환, 응답 영역 하이라이트 |
| 3 | 기능 발견 | 핵심 기능 1 하이라이트 (예: 지도/영상 확인) |
| 4 | 기능 발견 | 핵심 기능 2 하이라이트 (예: 결과 활용 — 다운로드/추가 질문) |
| 5 | 가입 전환 | "진짜 데이터로 써보려면 회원가입" 모달 — 튜토리얼의 클라이맥스이자 전환 지점 |

스텝 3-4의 실제 대상 기능은 캡쳐 준비 시 Clarity 데이터 기준으로 확정한다 (가장 발견 안 되는 기능 우선).

### 구현 스펙 (핸드오프 조건)

- `steps.ts`: `{ id, type: 'highlight' | 'modal', capture, hotspot: {x,y,w,h}, title, body, action }` 배열 — 이 파일이 곧 실구현 driver.js 설정의 원형. `type: 'modal'`(스텝 5)은 capture/hotspot/action 없이 모달 컴포넌트를 렌더링.
  - `hotspot` 좌표계: **캡쳐 원본 크기 대비 % 단위**. 캡쳐는 aspect-ratio 고정 컨테이너에 렌더링하고, 핫스팟 div는 % 기반 절대배치로 스케일 추종.
  - `action`: `'click'`(핫스팟을 직접 클릭해야 다음 스텝) `| 'next'`(말풍선의 다음 버튼으로 진행) 두 값만 허용.
- 오버레이: driver.js(MIT)를 데모에서 실제 사용 — 캡쳐 이미지 위 절대배치 투명 div를 타겟으로
- **스텝 간 캡쳐 전환**: driver.js는 단일 정적 페이지를 가정하므로, 스텝 훅(`onNextClick`/`onHighlightStarted`)에서 배경 캡쳐 이미지를 교체하고 하이라이트 위치를 재계산한다. **이 훅 기반 캡쳐 전환이 이 데모의 유일한 비자명(nontrivial) 구현 지점** — 나머지는 설정 작업.
- **스텝 5 가입 모달**: 캡쳐가 아니라 DESIGN.md 스타일의 실제 DOM 컴포넌트. CTA는 데모에서는 **비활성 — 클릭 시 "실서비스에서는 여기서 가입 플로우로 연결됩니다" 툴팁 표시** (재시작 순환은 승인자를 혼란시킬 수 있어 배제). 모달 하단에 별도 "데모 다시 보기" 텍스트 링크.
- 비로그인 시점 연출: 캡쳐를 비로그인 상태 화면으로 준비. **단, 스텝 2-4의 기능 화면이 비로그인으로 도달 불가하면 로그인 상태로 캡쳐 후 계정 UI를 크롭/블러 처리해 비로그인처럼 연출** (Dependencies에서 사전 확인).
- 진행 표시: 스텝 인디케이터 (완주율 모범사례 — 진행 가시화)
- 언제든 건너뛰기 가능 (강제 진행은 알려진 완주율 킬러) — **건너뛰기 시 스텝 5(가입 모달)로 점프** 후 아웃트로로 이동. 전환 지점은 항상 통과시킨다.
- 뷰포트: **데스크톱 전용(최소 1280px)** — 모바일 반응형은 프로젝트 결정에 따라 별도 태스크로 연기됨.

## Open Questions

1. **승인자가 누구인지 미확정** (대표/사업부서장/개발리드?) — 데모 완성도 기준과 회람 방식에 영향. 확정 필요.
2. 스텝 3-4에서 하이라이트할 **핵심 기능 2개의 선정** — Clarity에서 가장 발견 안 되는 기능 기준으로 캡쳐 준비 시 확정.
3. 제안용 라우트의 노출 방식 — 내부 배포 서버 전용 URL로 충분한지, 접근 제어 필요한지.
4. 실구현 시 Agent 서비스의 프론트 스택 확인 (React면 driver.js 또는 React Joyride 중 선택).

## Success Criteria

1. **1차 (페이지 자체)**: 승인자가 데모를 끝까지 클릭 완주하고, 제안이 greenlight됨.
2. **2차 (승인 후 실구현의 성공 지표 — 페이지 아웃트로에 명시)**: 첫 화면 이탈률 감소, 튜토리얼 완주율 ≥ 38%(3-5스텝 구간 벤치마크 완주율), 비로그인 → 가입 전환율 신규 측정.

## The Assignment

코드를 만지기 전에 할 일 하나: **Clarity에서 최근 30일 기준 수치 3개를 오늘 뽑아라** — ① 첫 화면(빈 입력창) 이탈률, ② 평균 체류 시간, ③ 방문→가입 전환율. 이 3개가 데모 도입부의 첫 문장이 되고, 승인 후에는 튜토리얼 효과를 측정할 베이스라인이 된다. 뽑는 김에 승인자와 15분 데모 일정도 잡아라 — 데모는 회람보다 직접 클릭시키는 자리에서 통과된다.

## What I noticed about how you think

- "각 플로우의 화면 자체는 캡쳐를 해서 그냥 넣어도 될 듯" — 처음부터 제작 비용을 최소로 잡는 스코핑 감각. 통념은 캡쳐 기반을 나쁘다고 하지만, 기획 시연에는 그게 정답이라는 걸 직관으로 먼저 짚었다.
- 전제 3을 그냥 동의하지 않고 "비로그인 상태에서 튜토리얼을 진행하고 진짜로 쓰고 싶으면 회원가입 모달"로 뒤집었다 — 범위 밖이라 제외하자던 가입 장벽 문제를 튜토리얼 안으로 끌어들여 전환 퍼널로 만든 것. 이 세션에서 가장 좋은 설계 결정이었고, 내가 아니라 당신이 냈다.
- 증언만이 아니라 Clarity 데이터를 이미 보고 있었다 — 감이 아니라 계기판을 보며 운전하는 타입.
